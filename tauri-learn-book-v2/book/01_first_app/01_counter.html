Tauri v2 实战练习（v2）

练习 01: 计数器

为什么要学这个

第一个练习不做花哨的事，但这一章要回答三个问题，它们决定你对 Tauri 的基本理解正确与否：

  1. 一个桌面应用为什么非要分“前端 + 后端“两个进程？ —— 界面归谁、能力归谁，为什么不能一个程序全干？
  2. “命令“到底是什么东西？ —— 为什么它不能是个普通函数？前端怎么够得着它？
  3. invoke 为什么必须写成异步的？ —— 你点一下按钮，背后到底发生了什么？

把这三件事搞懂，后面所有练习（状态、事件、文件、数据库、通知……）都只是这三件事的自然延伸。

从问题出发

练习 01 要做的事：桌面上一个按钮，点一下数字 +1。

用网页做这个需求，let count = 0; count++ 一行就写完了。但这里我们故意绕个弯：把“加一“这件事交给后端 Rust 去算。为什么？

因为真正的桌面应用里，前端做不了的事情太多了——读文件、查数据库、弹系统通知、访问剪贴板，这些能力全在 Rust 进程里。如果连“加一“这种最简单的调用都走不通，后面那些能力更无从谈起。 所以这道菜练的不是“计数器“，是 Tauri 的前后端调用链路。

核心矛盾： 前端跑在 WebView 里，本质是浏览器环境；Rust 进程是独立的系统进程。它们语言不同、内存不共享，中间隔着一道进程边界。Tauri 要解决的就是：让前端以最少的仪式调用到后端。

前端 (WebView)                   Rust 核心进程
┌──────────────────┐    IPC    ┌──────────────────────┐
│ 点按钮            │ ────────► │ count_up(current)    │
│ invoke("count_up")│ ◄──────── │ 算出 current + 1      │
│ 拿到结果并刷新界面 │           │ 返回结果              │
└──────────────────┘           └──────────────────────┘

Tauri 把这条链路抽象成三层，本课就讲这三层：

invoke()                 → 调用层：前端跨进程发起请求
#[tauri::command]        → 命令层：定义可被调用的后端函数
generate_handler!        → 注册层：把命令登记进"电话号码簿"

1. invoke() — 前端给后端打电话

前端的调用长这样：

const next = await invoke<number>("count_up", { current: count });
//                       ^^^^^^^^  ^^^^^^^^^^   ^^^^^^^^^^^^^^^^^^
//                       返回类型   命令名（字符串）   参数（对象）

拆开看三件事：

1. 命令名是一个字符串。 前端并不知道后端的函数在内存的哪个位置，它只能喊一个名字，后端按名字去查。所以 "count_up" 必须和后端注册的名字一字不差——拼错一个字，就是“命令未找到“。

2. 参数是一个对象，key 必须等于 Rust 参数名。 { current: count } 里的 current 对应 Rust 函数的参数 current: i32。Tauri 会把整个对象序列化成 JSON 传给后端，后端按参数名反序列化。key 拼错（比如 { cur: count }），后端会因参数缺失而报错。

3. 返回值用泛型 <number> 声明。 它对应 Rust 的 i32。注意这只是一个 TS 侧的声明，运行时不会校验——类型对不上时，显示的多半是 undefined。

关键理解： 前端的 invoke 和后端的函数执行，不是“同一块内存里的函数调用“，而是“两个独立进程的协作“。所以它必须异步——见第 4 节。

2. #[tauri::command] — 把函数升级成命令

后端定义命令：

#[tauri::command]
fn count_up(current: i32) -> i32 {
    current + 1
}

Rust 语言本身没有“命令“这个概念。#[tauri::command] 是一个属性宏，它在编译期把普通函数“升级“成框架可识别、可调用的单元，自动生成：

  1. 参数反序列化：把前端传来的 JSON 转成 current: i32
  2. 返回值序列化：把 i32 转成可回传前端的 JSON
  3. 注册信息：命令的名字与签名，供运行时查找

为什么用宏而不是手写？ 因为“反序列化 + 序列化“这套样板代码跟函数签名强相关。宏能分析签名自动生成；手写的话，每个命令都要重复一遍，还容易写错。

不加会发生什么： 函数本身编译通过，但前端 invoke("count_up") 时后端查无此命令，报“命令未找到“。

3. generate_handler! — 登记电话号码簿

命令定义了，还要登记，前端才调得到：

.invoke_handler(tauri::generate_handler![count_up])
  • generate_handler![...]：把列出的命令打包成一张“命令注册表“
  • .invoke_handler(...)：把这张表挂到 Builder 上

前端发来的每条调用请求，都在这张表里按名字查找。所以：写了 #[tauri::command] 但忘了登记 = 命令未找到；登记了但名字拼错 = 命令未找到。这是每个练习都会埋一次的坑。

4. serde 与序列化 — 两边讲同一种语言

前端和后端语言不同、进程不同，唯一的共同点就是：都能把数据变成 JSON 字节流。这一来一回的“翻译“，就是序列化（Rust → JSON）和反序列化（JSON → Rust）：

前端 JS                        IPC（JSON 字节流）             Rust
count = 3  ──►  {"current":3}  ──────────────────────►  current: i32 = 3
                  ◄──────────────────────  {"result":4}  ◄──  current + 1 = 4

本课用的 i32 / number 是基础类型，自带序列化能力，不需要额外声明。自定义结构体才需要 #[derive(serde::Serialize)] 声明“我能被序列化“——那是 a01 待办清单的内容，这里先把基础类型的地基打好。

知识点连起来看

┌──────────────────────────────────────────────┐
│ 前端 (WebView)                               │
│   invoke("count_up", { current })  ← 调用层   │
│                                              │
│ Rust 核心进程                                │
│   #[tauri::command] fn count_up  ← 命令层    │
│   generate_handler![count_up]     ← 注册层   │
└──────────────────────────────────────────────┘
层解决的问题关键概念
invoke()前端怎么发起调用IPC、Promise、async/await、参数对象
#[tauri::command]函数怎么被前端调用属性宏、参数反序列化、返回值序列化
generate_handler!前端按什么找到命令注册表、按名字查找

一通百通的核心： 这三个知识点是 Tauri 的调用链路——调用层发消息，命令层暴露能力，注册层做索引。后面要学的状态（a01）、异步（a03）、事件（a01）全都是在这条链路上叠加：链路怎么走，永远不变；变的只是命令里装了什么。

递进关系： 练习 02（a01 待办清单）将回答“数据该放哪“——Builder::manage() + State<T>，让后端能记住状态，不再像计数器这样每次把数字传过去。
