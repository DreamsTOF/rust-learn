# 练习 11: 条件 if

## 为什么要学这个

"条件渲染"——根据不同状态显示不同内容——是所有 UI 开发最基础的需求之一。几乎每个组件都有类似这样的逻辑：

- 如果用户已登录，显示用户名；否则显示"登录"按钮
- 如果数据加载中，显示加载动画；否则显示内容
- 如果表单校验失败，显示错误信息

在大多数框架中，条件渲染是一个"框架特性"——你需要学习一套专用的指令或语法（`v-if`、`*ngIf`、三元表达式等）。但在 Leptos 中，条件渲染没有任何新语法：**直接用 Rust 的 `if/else` 表达式。**

这就是这一节的核心洞见：**当模板语言和宿主语言合二为一时，"条件渲染"就不再是一个需要单独学习的概念了。**

---

## 问题：如果不能用 if/else，会怎样？

假设我们要显示一个布尔状态：

```rust
let (show, set_show) = signal(false);
```

没有原生的条件表达式，你可能会：

```rust
// 假想方案一：用一个特殊属性
<p if={show} class="visible">"内容"</p>    // ← 这不是 Leptos 语法

// 假想方案二：用三目运算符
<p>{show ? "已激活" : "未激活"}</p>        // ← Rust 没有三元运算符

// 假想方案三：先在外面算好
let text = if show.get() { "已激活" } else { "未激活" };
view! {
    <p>{text}</p>
}
```

方案三完全可用，是合理的写法。但它的缺点是：**条件逻辑脱离了模板上下文。** 阅读代码的人先看到一个 `if/else` 定义了一个 `text` 变量，然后在 `<p>` 中看到 `{text}`——他需要把这两处关联起来。

如果条件逻辑直接嵌入在模板中：

```rust
view! {
    <p>"当前状态: " { if show.get() { "已激活" } else { "未激活" } }</p>
}
```

条件逻辑和它影响的内容在同一个位置，阅读代码时一目了然。

> **设计原则：** 相关的内容应该放在一起。`if/else` 和它所控制的 UI 片段是高度相关的，把它们分开（变量在模板外、引用在模板内）会增加认知成本。

## 在 view! 中使用 if/else

### 基础语法

```rust
let (show, set_show) = signal(false);

view! {
    <p>
        "当前状态: "
        { if show.get() { "已激活" } else { "未激活" } }
    </p>
}
```

这个 `{ }` 块内部是一个完整的 Rust `if/else` 表达式：

```
{ if show.get() { "已激活" } else { "未激活" } }
├┘└┬────────────────────────────────────┬┘
│  │                                    │
│  └── Rust if/else 表达式               │
│      ├ 条件: show.get() → bool       │
│      ├ true 分支: "已激活" (&str)    │
│      └ false 分支: "未激活" (&str)   │
│                                       │
└── view! 的 { } 模式切换到 Rust 模式
```

**注意：** `if/else` 本身就是 Rust 的表达式，`view!` 宏没有做任何特殊处理。它的行为与写在 view! 外部完全一致。

### 为什么要用 `move ||` 闭包包装？

如果你仔细看答案代码，会发现这样写：

```rust
{ move || if show.get() { "已激活" } else { "未激活" } }
```

注意这里多了一层 `move ||` 闭包。这不是普通的静态条件——这是一个**动态的、响应式的条件**。

解释一下区别：

```rust
// 静态条件（一次计算，永远不会更新）
{ if show.get() { "已激活" } else { "未激活" } }

// 动态条件（每次信号变化时重新计算）
{ move || if show.get() { "已激活" } else { "未激活" } }
```

`move ||` 闭包告诉 Leptos："这段代码依赖于 `show` 信号，当 `show` 变化时，需要重新执行这个闭包。"

如果不加 `move ||`，`show.get()` 只会在首次渲染时计算一次，之后信号变化了视图也不会更新。

> **这个机制在后面的"响应式"章节会详细展开。** 目前只要记住：**当你想让条件随着信号动态变化时，就需要 `move ||` 包装。静态条件（值永远不会变）可以不用闭包。**

### if/else 的链式分支

`if/else` 在 Rust 中可以链式扩展：

```rust
{
    let score = 85;
    if score >= 90 {
        "优秀"
    } else if score >= 60 {
        "及格"
    } else {
        "不及格"
    }
}
```

在 view! 中同样支持，完全遵循 Rust 语法规则：

```rust
view! {
    <p>
        "评分: "
        {
            let score = 85;
            if score >= 90 {
                "优秀"
            } else if score >= 60 {
                "及格"
            } else {
                "不及格"
            }
        }
    </p>
}
```

## 条件渲染的三种形式

条件渲染在 Leptos 中有三种常见模式：

| 形式 | 适用场景 | 示例 |
|------|---------|------|
| if/else 表达式 | 二选一或三选一的文本/元素 | `{if cond { "A" } else { "B" }}` |
| 块表达式 + if | 复杂条件逻辑 | `{{ let x = ...; if x > 0 { ... } }}` |
| 响应式闭包 | 信号驱动的动态条件 | `{move || if signal() { ... }}` |

### 什么时候用 `if` 不带 `else`？

Rust 要求 `if` 表达式**必须有 `else` 分支**，因为表达式必须有一个确定的值：

```rust
// ❌ 编译错误：if 表达式没有 else 分支
{
    if show.get() { "可见" }
}

// ✅ 正确：有 else 分支
{
    if show.get() { "可见" } else { "" }
}
```

如果你想实现"条件满足时显示 A，否则什么都不显示"，有两种写法：

```rust
// 方式一：else 返回空字符串
{ if show.get() { "可见" } else { "" } }

// 方式二：用 Option（后面章节会学到）
// { show.get().then(|| "可见") }
```

> **为什么 Rust 强制 else？** 这与类型安全有关。如果 `if` 可以没有 `else`，那 `if cond { 42 }` 在 `cond` 为 false 时的类型应该是 `()`——但 Rust 在编译期不知道 `cond` 的值，所以它不知道这个表达式的类型到底是 `i32` 还是 `()`。强制 `else` 消除了这种不确定性。

## 条件渲染什么：文本 vs 元素

到目前为止我们条件渲染的都是**文本节点**。但 `if/else` 完全可以用在**元素**上：

```rust
{ if show.get() {
    view! { <span>"已激活"</span> }
} else {
    view! { <strong>"未激活"</strong> }
}}
```

注意：`if` 和 `else` 分支返回的东西必须实现同一个 trait（这里是 `IntoView`）。`view! { <span>...</span> }` 返回 `HtmlElement`，它实现了 `IntoView`。

但你不能这样：

```rust
// ❌ 编译错误：分支类型不一致
{
    if show.get() {
        "文本"                                   // &str
    } else {
        view! { <span>"元素"</span> }             // HtmlElement
    }
}
```

两个分支的类型必须相同，否则 Rust 类型系统会拒绝编译。解决方案是确保两边的返回类型一致：

```rust
// ✅ 两边都返回 HtmlElement
{
    if show.get() {
        view! { <span>"文本"</span> }
    } else {
        view! { <span>"元素"</span> }
    }
}
```

## 与其他框架的对比

| 框架 | 条件渲染语法 | 是否表达式 |
|------|------------|-----------|
| Leptos | `{ if cond { A } else { B } }` | ✅ 是（Rust 表达式） |
| React | `{ cond ? <A/> : <B/> }` | ✅ 是（JS 三元表达式） |
| Vue | `<div v-if="cond">A</div>` | ❌ 指令（非表达式） |
| Svelte | `{#if cond} A {:else} B {/if}` | ❌ 模板块语法 |
| Angular | `<div *ngIf="cond">A</div>` | ❌ 结构型指令 |

Leptos 是唯一一个**直接在模板中使用宿主语言原生条件表达式**的主流框架。其他框架要么引入专用指令（Vue、Angular），要么发明模板块语法（Svelte），要么依赖三元运算符（React 的 JSX 无法直接使用 JS 的 `if`）。

> **为什么 React 不能在 JSX 中用 `if`？** 因为 JSX 是 JavaScript 的语法扩展，`if` 在 JavaScript 中是语句（statement），不是表达式（expression）。JSX 的 `{ }` 内只能放表达式。但 Rust 的 `if` 是表达式——所以 Leptos 不需要折中方案。

## 总结

| 概念 | 要点 |
|------|------|
| 为什么用 if/else | 条件渲染是 UI 最基本的需求——根据状态显示不同内容 |
| 语法 | `{ if cond { "A" } else { "B" } }` |
| 必须要有 else | Rust 表达式要求所有分支返回类型一致 |
| 动态条件 | 需要 `move ||` 包装以保证信号变化时重新计算 |
| 文本 vs 元素 | 都可以——只要分支类型统一 |
| Rust 的优势 | `if/else` 是表达式，不需要像 JSX 那样用三元运算符替代 |

**一通百通：** 条件渲染在大多数框架中是一个"需要学习的概念"，因为在那些框架中，模板语言和宿主语言是分离的。但在 Leptos 中，条件渲染就是 Rust 的 `if/else`——不添加任何新概念。这意味着你对 Rust 条件表达式的所有知识——模式匹配、`if let`、链式 `else if`——全部可以直接用在模板中。**Leptos 不发明自己的条件渲染语法，因为 Rust 已经给了你最好的那一套。**
