# 练习 18: Fragment 多根节点

## 为什么要学这个

写 HTML 时，一个容器元素只能有一个根。但写组件时，你经常需要返回多个兄弟元素——一个标题、一段说明、一个按钮并列在一起。

最自然的想法是包一层 `<div>`：

```rust
#[component]
fn Card() -> impl IntoView {
    view! {
        <div>
            <h2>"标题"</h2>
            <p>"内容"</p>
            <button>"操作"</button>
        </div>
    }
}
```

问题解决了？从"必须一个根"的角度看，是的。但从"我的 DOM 结构"的角度看，这个 `<div>` 可能是个麻烦：

- **CSS Flexbox / Grid 布局** — 如果 `Card` 是某个 flex 容器的子元素，多出的 `<div>` 会破坏布局结构
- **选择器干扰** — `div > *` 或 `:first-child` 等 CSS 选择器会受额外嵌套层影响
- **语义污染** — 多余的包装元素没有语义意义，只是框架约束的产物
- **性能** — 多余的 DOM 节点虽然影响微小，但积少成多

**核心矛盾：** 每个组件必须返回一个根元素，但这个根元素在你的 UI 树中可能是多余的。你需要的是一种"存在但不产生 DOM 节点"的包装方式——这就是 Fragment。

---

## 从问题出发

### 为什么组件必须"一个根"？

这实际上不是 Leptos 的约束，而是**组件函数返回值类型**的天然限制：

```rust
fn Card() -> impl IntoView {
    // 只能返回一个东西
    // 不能返回 "一个 <h2>、一个 <p>、一个 <button>"
}
```

`impl IntoView` 代表"一个视图"。你不可能让一个函数同时返回值 A、值 B、值 C 而不把它们打包。

解决方案有两个：

| 方案 | 做法 | DOM 影响 |
|------|------|---------|
| 包装元素 | 包一层 `<div>` | 增加一个 DOM 节点 |
| Fragment | 包一层 `<></>` | 不产生额外 DOM 节点 |

Fragment 在概念上也是一个"打包盒"，但这个盒子在 DOM 中不可见——里面的元素直接成为父容器的子元素。

```
用 <div> 包装:
父容器 ── <div> ── ├── <h2>
                   ├── <p>
                   └── <button>

用 <></> Fragment:
父容器 ── ├── <h2>
          ├── <p>
          └── <button>
```

> **直观理解：** `<div>` 是一个实体的盒子——你把三个物品放进去，外面的人看到的是"一个盒子"。而 Fragment 是一个虚拟的打包袋——你把三个物品放进去，外面的人直接看到三个物品，包装袋在视觉上不存在。

---

## Fragment 语法：`<></>`

### 基本使用

```rust
view! {
    <>
        <h2>"标题"</h2>
        <p>"内容段落一"</p>
        <p>"内容段落二"</p>
    </>
}
```

这就是 Fragment 最简单的形式——一对空的尖括号 `<>` 和 `</>`，包裹多个子元素。

### Fragment 的本质

Fragment 在 Leptos 中是一个特殊的类型，它的 `IntoView` 实现被设计成**不产生实际的 DOM 节点**。它的展开过程大致如下：

1. `view!` 宏识别到 `<></>`，生成对应 Fragment 代码
2. 运行时，Fragment 依次渲染其子元素
3. 子元素直接附加到 Fragment 的父节点上，Fragment 本身不创建 DOM 节点

所以从浏览器 DOM 的视角看，Fragment "不存在"——你用 DevTools 检查元素时，看不到任何代表 Fragment 的节点。

> **与 JavaScript 的 Fragment 对比：** React 在 16.2 引入了 Fragment 支持，底层使用 `React.Fragment` 类型。Leptos 的设计完全相同，只是语法上用了更简洁的 `<>`（React 在 16.4 后也支持了同样的语法）。这不是巧合——这是业界对"虚拟容器"需求的标准回应。

## Fragment 嵌套

Fragment 可以包含 Fragment：

```rust
view! {
    <>
        <h2>"外层标题"</h2>
        <>
            <p>"内层段落一"</p>
            <p>"内层段落二"</p>
        </>
    </>
}
```

效果跟不嵌套完全一样——所有 `<h2>` 和两个 `<p>` 都直接成为父容器的子元素。嵌套 Fragment **没有额外的 DOM 开销**。

为什么需要嵌套？通常是代码组织的需要——比如条件渲染中，一个 `if` 分支内需要返回多个元素：

```rust
view! {
    <>
        <h2>"用户信息"</h2>
        {if logged_in() {
            // 这个分支需要返回多个元素，用 Fragment 包装
            view! { <>
                <p>"欢迎回来！"</p>
                <button>"退出登录"</button>
            </>}
        } else {
            view! { <p>"请先登录"</p> }
        }}
    </>
}
```

这里的嵌套 Fragment 不是"炫技"，而是代码逻辑的自然结果——`if` 分支需要返回一个单一的 `impl IntoView`，嵌套 Fragment 提供了这个"单一包装"而不影响 DOM。

## 空 Fragment

Fragment 中可以放 0 个元素：

```rust
view! {
    <>
        <h2>"标题"</h2>
        <></>
    </>
}
```

空 Fragment 是一个特殊的构造——它代表"什么都没有"。这在条件渲染中非常有用：

```rust
view! {
    <>
        <h2>"通知"</h2>
        {if has_notifications() {
            view! { <p>"你有新消息"</p> }
        } else {
            // 返回空 Fragment ≈ 什么都不渲染
            view! { <></> }
        }}
    </>
}
```

空 Fragment 等价于"不渲染任何内容"。它比返回 `()` 或 `None` 更明确——在 `view!` 的上下文中，`<></>` 清晰地表达了"这里什么都不显示"的意图。

---

## 有 Fragment vs 无 Fragment

| 场景 | 用 `<div>` 包装 | 用 `<></>` Fragment |
|------|----------------|-------------------|
| DOM 节点数 | 增加一个 `<div>` | 不增加 |
| Flex/Grid 布局 | 包装 div 会影响子项布局 | 子项直接参与布局 |
| CSS 选择器 | `:first-child` 选中 div | `:first-child` 选中第一个实际元素 |
| 语义 | 纯结构包装，无语义 | 完全不影响语义 |
| 点击事件范围 | div 的区域拦截事件 | 不影响事件传播 |
| 代码可读性 | 视觉效果明显 | 略微抽象（需理解 Fragment） |

---

## 一个原则

```
每个 Fragment 都意味着："这些元素应该在一起，但没有必要包一层 DOM。"
```

Fragment 解决的根本问题是：**组件化思维与 DOM 树结构之间的矛盾**。组件是逻辑的单元，它需要返回"一个视图"；但 DOM 是结构的树，它不关心你的组件划分。

Fragment 就像组件逻辑和 DOM 结构之间的防火墙——让你在组件层面自由组织代码，同时不污染 DOM 层。写组件时优先考虑 Fragment，只有当 Fragment 不够用（需要样式、事件、语义）时才升级到 `<div>` 或其他容器元素。

这个选择不是过早优化——不在 DOM 中插入多余节点，是对布局系统、CSS 选择器和渲染性能的基本尊重。
