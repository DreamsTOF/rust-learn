# 练习 01: Hello World

## 为什么要学这个

写一个 Hello World 不是为了凑数。这一章要回答三个问题，它们决定了你对 Leptos 的基本理解正确与否：

1. **一个 Web 框架的入口点意味着什么？** — 从 Rust 的 `main()` 到网页的 `<body>`，中间发生了什么？
2. **"组件"到底是一个什么东西？** — 为什么框架都要发明这个概念？它不是 HTML，也不是 Rust 函数，那它是什么？
3. **为什么需要 `view!` 这样一个独立的宏来写 UI？** — 直接写 HTML 不行吗？字符串拼接不行吗？

如果把这三件事理解透了，后面所有章节（响应式、事件、路由）就只是这三件事的自然延伸。

---

## 从问题出发

在网页上显示一段文字，最原始的方式是：

```html
<p>Hello, World!</p>
```

但这是 HTML，不是 Rust。我们要用 Rust（编译成 WASM）来做同样的事。

**核心矛盾：** Rust 没有内建"操作网页"的能力。WASM 可以调用 DOM API，但那是 C 风格的底层接口，像这样：

```javascript
// JavaScript
document.createElement('p');
p.textContent = 'Hello, World!';
document.body.appendChild(p);
```

这在 Rust 里也能写，但极其繁琐。Leptos 要解决的问题很简单：**给你一套 Rust 语言层面的抽象，让你用 Rust 的方式描述 UI，它来负责翻译成 DOM 操作。**

这个抽象分三层：

```
你写的 Rust 代码           Leptos 运行时         浏览器 DOM
┌────────────────┐       ┌──────────────┐       ┌──────────┐
│ mount_to_body() │ ───► │ 创建根容器     │ ───► │ <body>   │
│ #[component]    │ ───► │ 定义组件      │ ───► │ 自定义元素 │
│ view! { ... }   │ ───► │ 生成 DOM 树   │ ───► │ 实际 DOM  │
└────────────────┘       └──────────────┘       └──────────┘
```

这三层就是本节的三个知识点。下面逐一展开。

---

## 1. `mount_to_body` — 为什么需要一个"挂载点"？

### 最直接的问题

你的 Rust 程序跑在 WASM 里。WASM 模块没有自己的屏幕——它不能像桌面程序那样直接画窗口。它只能**通过 JavaScript 间接操作浏览器 DOM**。

所以第一个问题就是：**"我的 UI 应该放在网页的哪个位置？"**

这就是 `mount_to_body` 回答的问题：

```rust
fn main() {
    mount_to_body(App);
}
```

### 为什么是 `<body>`，而不是别的地方？

`mount_to_body` 是 Leptos 提供的最简单入口，它在 `<body>` 元素的末尾插入你的应用。

理论上你可以挂载到任意 DOM 元素（比如 `<div id="app">`），Leptos 也提供了 `mount_to` 函数来做这个。但 `mount_to_body` 贵在简单——对新学者来说，少一个配置就少一个困惑。

> **设计思路：** 框架的默认入口要满足"零配置可用"。`mount_to_body` 就是这样一个默认——你不需要先准备一个 HTML 模板，不需要指定挂载点，框架帮你选了最通用的 `<body>`。

### `main` 函数执行完就结束了吗？

```rust
fn main() {
    mount_to_body(App);
    // 执行完这行之后呢？
}
```

通常的 Rust 程序，`main` 结束进程就退出了。但在 Web 应用中，`main` 结束**之后程序还在运行**。

这是因为 `mount_to_body` 内部做了两件事：

1. **设置了 Leptos 的运行时**（响应式系统的调度器、DOM 更新队列等）
2. **注册了事件循环**（等待用户点击、网络请求等）

所以 `main` 执行完后，Leptos 的运行时接管了控制权，等待各种事件发生。这跟 Node.js 的 `event loop` 或浏览器的 `requestAnimationFrame` 是同一个模式。

> **关键理解：** WASM 应用不是"一次性计算"，而是"驻留程序"。`main` 只是初始化步骤，真正的生命周期在 mount 之后才开始。

### 为什么从 0.7 到 0.8 API 变了？

很多初学者会看到新老两种写法：

```rust
// Leptos 0.7 及之前
fn main() {
    mount_to_body(|| App());
}

// Leptos 0.8
fn main() {
    mount_to_body(App);
}
```

为什么变了？因为 0.8 的 `#[component]` 宏生成的代码可以直接作为函数指针传递，不需要闭包包装。这个变化的好处是：**一个组件就是一个普通的 Rust 函数**，不依赖闭包捕获，类型更简单，编译更快。

这个细节说明了 Leptos 的一个设计方向：**尽可能让组件看起来像普通 Rust 函数**，减少框架特有的仪式。

## 2. `#[component]` — 为什么需要"组件"？

### 一个函数不够吗？

如果你只想显示一个 Hello World，确实不需要组件，直接：

```rust
fn main() {
    mount_to_body(|| {
        view! { <p>"Hello, World!"</p> }
    });
}
```

但现实中的应用有几百个 UI 片段，分散在几十个页面里。**你需要一种方式把 UI 片段打包成可复用的单元。**

这就是组件的由来。

### 组件 = 函数 + 状态 + 生命周期

一个组件本质上就是一个函数，但比函数多了三样东西：

| | 普通函数 | 组件 |
|---|---|---|
| 输入 | 参数 | 属性（Props） |
| 输出 | 返回值 | 视图（DOM 树） |
| 可调用次数 | 无限 | 按需，框架控制 |
| 是否有状态 | 无 | 可以有（Signal） |
| 由谁管理 | 调用者 | 框架 |

```rust
// 普通函数 — 每次主动调用
fn greet(name: String) -> String {
    format!("Hello, {name}!")
}

// 组件 — 由框架在适当时候渲染
#[component]
fn Greeting(name: String) -> impl IntoView {
    view! { <p>"Hello, " {name} "!"</p> }
}
```

**核心区别：** 你调用 `greet("World")`，立即得到字符串。你声明 `<Greeting name="World"/>`，框架决定**何时**调用这个函数、**是否**缓存结果、**何时**重新执行。

> **为什么框架要接管"何时调用"？** 因为 UI 需要响应变化——某个状态变了，框架要自动重新渲染受影响的部分，而不是手动调用每个组件。

### 为什么用 `#[component]` 宏？

Rust 语言本身没有"组件"这个概念。`#[component]` 是一个**属性宏**，它在编译期把你的函数"升级"成框架可以识别和管理的单元。

这个宏做了几件事：

1. **生成组件注册代码** — 告诉 Leptos 运行时：这个函数是一个组件，它的名字是 `Greeting`，它接受哪些参数
2. **实现 `IntoView`** — 使得组件可以在 `view!` 中通过 `<Greeting/>` 调用（否则只是一个普通函数）
3. **参数包装** — 函数的参数自动成为组件的 props（属性），可以在 `<Greeting name="..."/>` 中传入

```rust
// 你写的
#[component]
fn Greeting(name: String) -> impl IntoView { ... }

// 宏大致生成（简化）
// 1. 一个结构体 GreetingProps { name: String }
// 2. 一个为 GreetingProps 实现的 IntoView
// 3. 注册函数以便运行时能找到它
```

> **为什么用宏而不是 trait？** 因为 trait 无法处理"函数参数自动变成 props 结构体字段"这种需求。宏可以分析函数签名，生成对应的 props 结构体和转换代码。这是 Rust 中"编译期元编程"的典型应用。

### 为什么组件名必须 PascalCase？

这不是 Leptos 的任性决定，而是 `view!` 宏的语法需要：

```rust
view! {
    <greeting/>  // 宏会解析为 HTML 元素 <greeting>（不存在）
    <Greeting/>  // 宏会解析为 Leptos 组件
}
```

大小写是 `view!` 宏区分 **HTML 元素**和 **自定义组件**的唯一依据。HTML 标签都是小写的（`div`、`p`、`span`...），所以大写开头的就是组件。

> 这个约定跟 React 的 JSX 完全一致。如果你用过 JSX，可以无缝迁移这个认知。

### `impl IntoView` 到底是什么？

```
IntoView
├── 实现了它的类型：
│   ├── HtmlElement<...>  ← view! 宏返回的主要类型
│   ├── String            ← 可以直接返回字符串
│   ├── i32, f64          ← 数字也可以
│   └── Vec<impl IntoView> ← 列表
│
└── 作用：作为"视图"的统一接口，
    不管内部是单个元素、文本、还是组件，
    对外都表现为一个 `impl IntoView`
```

**为什么需要这个 trait？** 因为 `view!` 宏可以返回很多种类型——单个 `<p>` 元素、多个元素的 Fragment、数字、字符串……组件函数需要一种统一的方式来表达"我返回的是视图"。

`impl IntoView` 这个写法，相当于告诉调用者："我返回一个东西，你可以把它当作视图来处理，但具体类型你不用管。"

> **设计原则：** 类型擦除（type erasure）。让组件函数的返回值保持灵活，不暴露内部实现细节。如果写成 `fn Greeting() -> HtmlElement`，那这个组件就永远不能返回 Fragment 或其他类型了。

## 3. `view!` 宏 — 为什么需要一个"DSL"？

### 不用宏的话怎么写 UI？

假设没有 `view!` 宏，用纯 Rust 创建 DOM 是这样的：

```rust
// 伪代码 — 实际 Leptos 的构建器 API
fn App() -> impl IntoView {
    leptos::html::p()
        .child("Hello, Leptos!")
        .into_any()
}
```

这个写法本身没问题（Leptos 也提供了构建器 API 作为 `view!` 的替代方案，后面的练习会涉及）。但它有几个缺点：

- **冗长** — 每个元素都需要函数调用
- **嵌套结构不直观** — 树形结构用函数嵌套表达，读起来费力
- **与 HTML 知识脱节** — 有 HTML/CSS 经验的人要重新学一套 API

`view!` 宏就是为了解决这些问题。

### `view!` 做了什么？

```rust
view! { <p>"Hello, Leptos!"</p> }
```

在编译期，这个宏展开成类似这样的代码：

```rust
// 近似展开
leptos::html::p().child("Hello, Leptos!")
```

**关键的差异：** 这个转换发生在**编译期**，不是运行时。这意味着：

1. **零运行时开销** — 没有模板解析、没有字符串拼接、没有虚拟 DOM diff
2. **编译期类型检查** — 属性名拼错了、标签没闭合，编译器直接报错，不会等到运行时才发现
3. **IDE 支持** — Rust Analyzer 可以正确理解宏内的代码（前提是 nightly 工具链）

> **与字符串模板的对比：** 很多框架用字符串模板（Handlebars、Mustache）。它们在运行时解析模板，有性能开销，而且类型不安全（你传错了数据类型，运行时才知道）。`view!` 在编译期就把模板展开成了类型安全的 Rust 代码。

### 为什么文本要加双引号？

这是初学者最容易困惑的地方：

```rust
view! {
    <p>"Hello, Leptos!"</p>  // ✅ 正确
    <p>Hello, Leptos!</p>    // ❌ 错误
}
```

原因在于 `view!` 宏解析 `{ }` 和 `"..."` 的规则：

- `{ 表达式 }` — 大括号内的内容被解析为 **Rust 代码**
- `"文本"` — 双引号内的内容被解析为 **文本字符串**
- **没有任何括号/引号包裹的内容被认为是 Rust 标识符**——`Hello` 会被当作 Rust 变量名来解析

所以 `<p>Hello</p>` 会被宏看作"找变量 `Hello`"，而不是"显示文本 Hello"。

> **设计动机：** 这种语法看似繁琐，但其实是为了消除歧义。JSX 中 `<p>Hello</p>` 是可用的，因为 JavaScript 有块级作用域的标识符解析，但 Rust 宏没有这种上下文。Rust 宏的解析更"字面"——你需要明确告诉宏：这是文本，还是代码。

### 为什么用 `{ }` 嵌入 Rust 代码？

```rust
view! {
    <p>{42}</p>
    <p>{format!("计算结果: {}", 1 + 1)}</p>
    <p>{if true { "真" } else { "假" }}</p>
}
```

大括号在 `view!` 中是一个"Rust 模式切换"——进入 `{ }` 后，宏暂时退出"HTML 模式"，进入"Rust 模式"。里面的内容直接作为 Rust 代码编译。

这个设计让 `view!` 既有 HTML 的声明式语法，又能无缝嵌入 Rust 逻辑。

> **与 JSX 的对比：** JSX 也用 `{}` 嵌入 JavaScript 表达式。但 JSX 只能嵌入表达式（有值的代码段），而 Leptos 的 `view!` 可以嵌入任意 Rust 代码——包括 `if`、`match`、`loop` 等语句。这是因为 Rust 的 `{ }` 本身就是表达式，可以包含语句。

### 我是 React 开发者，有什么要注意的？

| 概念 | React (JSX) | Leptos (view!) |
|------|------------|----------------|
| 文本节点 | `<p>Hello</p>` | `<p>"Hello"</p>` |
| 嵌入表达式 | `<p>{name}</p>` | `<p>{name}</p>` |
| 属性 | `className="box"` | `class="box"` |
| 事件 | `onClick={handler}` | `on:click=handler` |
| 条件渲染 | `{cond && <A/>}` | `{if cond { view!{<A/>} } else { view!{<B/>} }}` |
| 列表 | `{list.map(i => <li/>)}` | `{list.into_iter().map(|i| view!{<li/>})}` |

最核心的区别就是**文本节点必须加双引号**。记住这一点，其他语法都很接近。

## 三个知识点连起来看

```
┌──────────────────────────────────────────────┐
│ 你的 Rust 代码                                │
│                                              │
│  fn main() {                                 │
│      mount_to_body(App);    ← 入口：挂载        │
│  }                                           │
│                                              │
│  #[component]               ← 声明：这是个组件   │
│  fn App() -> impl IntoView {                 │
│      view! {                 ← UI：描述界面     │
│          <p>"Hello, Leptos!"</p>              │
│      }                                       │
│  }                                           │
└──────────────────────────────────────────────┘
```

三个知识点是层层递进的：

| 层 | 解决的问题 | 关键概念 |
|----|-----------|---------|
| `mount_to_body` | WASM 没有屏幕，需要把 UI 挂到 DOM 上 | 入口点、运行时、事件循环 |
| `#[component]` | 需要把 UI 片段打包成可复用单元 | 属性宏、类型擦除、函数 vs 组件 |
| `view!` | 需要简洁、类型安全的方式描述 UI | 编译期宏、DSL、HTML 兼容语法

**一通百通的核心：** 这三个知识点反映的是 Leptos（以及大多数现代 Web 框架）的三个基础层——**入口层、组件层、视图层**。后面要学的响应式（Signals）、事件处理、路由，都是在这三层的基础上叠加的。入口层决定"从哪里开始"，组件层决定"怎么组织"，视图层决定"怎么描述"。
