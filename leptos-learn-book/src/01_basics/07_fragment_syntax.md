# 练习 07: Fragment 语法

## 为什么要学这个

Fragment（片段）解决一个看起来很小、但实际上所有组件库都必须面对的问题：**一个函数只能返回一个值，但 UI 有时候需要并列渲染多个兄弟节点。**

如果你从来没想过这个问题，那说明你一直在用 `<div>` 包住一切。这确实能工作，但不是好习惯——多余的 DOM 节点会让 HTML 结构臃肿、CSS 选择器复杂化、布局意外出错。

Fragment 要告诉你的是：**不是所有的分组都需要一个容器。有时候"无形的分组"才是正确的选择。**

---

## 问题：为什么组件不能直接返回多个元素？

### 从一个简单的布局说起

你想渲染一个标题和两个段落，它们是并列关系：

```html
<h2>Fragment 语法</h2>
<p>这是第一个段落</p>
<p>这是第二个段落</p>
```

在 HTML 里这完全合法——多个元素可以并列放在 `<body>` 或任何容器中。

但在 Leptos（以及 React、Vue 等）中，每个组件的返回值必须是一个单一节点：

```rust
#[component]
fn Exercise() -> impl IntoView {
    // 只能返回一个东西——一个 <div>、一个 <>、或一个单一元素
}
```

`impl IntoView` 只允许返回一个东西。你不能突然返回 `Vec<HtmlElement>`。这就是矛盾所在：你的 UI 逻辑上是多根的，但框架类型系统要求单根。

### 最简单的"解决方案"：套一个 `<div>`

```rust
#[component]
fn Exercise() -> impl IntoView {
    view! {
        <div>
            <h2>"Fragment 语法"</h2>
            <p>"这是第一个段落"</p>
            <p>"这是第二个段落"</p>
        </div>
    }
}
```

这能通过编译，完全合法。但它在 DOM 中产生了一个额外的 `<div>`：

```
渲染后的 DOM:
<body>
  <div>       ← 这个 div 是多余的！
    <h2>Fragment 语法</h2>
    <p>这是第一个段落</p>
    <p>这是第二个段落</p>
  </div>
</body>
```

这个 `<div>` 本身没有语义——它不是一个区块、不是导航、不是文章。它只是为了满足"返回值必须是一个节点"这个技术限制而存在的。

> **多余 DOM 节点的危害：**
> - 破坏 CSS 选择器（比如 `body > p` 直接选择失效，因为你插了一个 `<div>`）
> - 干扰 flex/grid 布局（多余的包装元素会让弹性盒子的子元素关系变得不直接）
> - 增加 DOM 树深度（对可访问性和性能都有负面影响）
> - 造成语义污染（无关的 `<div>` 会让 HTML 结构更难理解）

---

## Fragment：无包装的多根节点

Fragment 的语法极其简单：

```rust
view! {
    <>
        <h2>"Fragment 语法"</h2>
        <p>"这是第一个段落"</p>
        <p>"这是第二个段落"</p>
    </>
}
```

`<>` 和 `</>` 就是 Fragment 的打开和关闭标签。它跟普通的 HTML 标签用法一样，只是**标签名是空的**。

渲染后的 DOM：

```
<body>
  <h2>Fragment 语法</h2>
  <p>这是第一个段落</p>
  <p>这是第二个段落</p>
</body>
```

没有多余的 `<div>`、没有包装层。Fragment 在 DOM 中完全透明——它只存在于编译时的模板结构中，运行时不会产生任何对应节点。

> **Fragment 的物理比喻：** 它像是一个"虚拟的收纳盒"——编译时把多个子元素打包成一个值（满足 Rust 类型系统），但在运行时这个盒子自动消失，里面的东西直接散落在父容器中。

---

## Fragment 的内部机制

### Fragment 到底是什么？

Fragment 在 Leptos 中不是 HTML 元素——它不对应任何 DOM 接口。它只是一个**编译期的概念**。

在 `view!` 宏展开时，`<>...</>` 会被翻译成 `Fragment` 类型的值。`Fragment` 实现了 `IntoView`，所以它可以作为组件的返回值。

```
view! { <> ... </> }
        │
        ▼
// 编译时展开为（简化）:
leptos::Fragment::from([
    leptos::html::h2().child("Fragment 语法"),
    leptos::html::p().child("这是第一个段落"),
    leptos::html::p().child("这是第二个段落"),
])
        │
        ▼
// 运行时:
Fragment 被展开，子元素直接添加到父容器
```

### Fragment vs `<div>` 包装

| | Fragment | `<div>` 包装 |
|---|---|---|
| DOM 额外节点 | 无 | 有（一个 `<div>`） |
| 语义污染 | 无 | 可能 |
| CSS 选择器干扰 | 无 | 会改变层级关系 |
| 布局影响 | 无 | 可能破坏 flex/grid |
| 类型安全 | ✅ 框架级 | ✅ HTML 级 |

### Fragment 可以嵌套吗？

可以。Fragment 只是"透明打包"，可以多层嵌套：

```rust
view! {
    <>
        <>
            <p>"深层嵌套的 Fragment"</p>
        </>
    </>
}
```

渲染结果等同于一个 `<p>` 直接显示——所有 Fragment 层都在运行时塌缩了。不过实践中极少需要嵌套 Fragment。

## 与其他框架的对比

| 框架 | Fragment 语法 | 是否产生额外 DOM |
|------|-------------|----------------|
| Leptos | `<>...</>` | 否 |
| React | `<>...</>` 或 `<Fragment>` | 否 |
| Vue 3 | `<template>`（多根组件） | 否 |
| Svelte | 隐式支持 | 否 |
| Angular | `<ng-container>` | 否 |

几乎所有现代框架都提供了 Fragment 机制。它们的动机完全一致：**让组件可以返回多个根节点，而不污染 DOM 树。**

> **一个历史注解：** React 在 16.2 版本才引入 Fragment。在那之前，React 开发者要么用 `<div>` 包一切，要么用一个叫做 `react-aux` 的第三方库。Fragment 的出现让"隐含的包装"成为框架的一等公民——这之后几乎所有框架都跟进了这个设计。

---

## view! 宏的多根节点隐式支持

实际上，在 Leptos 的 `view!` 宏中，如果你直接写多个并列元素而不显式使用 `<>...</>`，宏也会自动为你包裹一层 Fragment：

```rust
view! {
    <h2>"标题"</h2>
    <p>"段落一"</p>
    <p>"段落二"</p>
}
```

这和显式写 `<>...</>` 的效果完全一样。但实践中，显式使用 Fragment 有两个好处：

1. **可读性** — 阅读代码的人一眼就能看到"这里有多个根节点"
2. **明确意图** — 告诉后来的维护者："这不是忘记加 `<>`，而是有意为之"

> **风格建议：** 如果 `view!` 内部只有**一个**顶层子元素，不需要 Fragment。如果有**多个**并列子元素，显式加上 `<>...</>` 让意图更清晰。

## 总结

| 概念 | 要点 |
|------|------|
| 为什么需要 | 组件只能返回单一值，但 UI 可能需要多个根节点 |
| Fragment 是什么 | 一个在运行时透明的容器，编译时打包子元素 |
| 语法 | `<>...</>` |
| DOM 影响 | 零——Fragment 不产生任何 DOM 节点 |
| 替代方案 | `<div>` 包装（有副作用） |
| 隐式支持 | `view!` 宏自动为多根节点包裹 Fragment |

**一通百通：** Fragment 是"零成本抽象"在 UI 框架中的经典体现。它解决的是一个类型系统的约束问题（函数只能返回一个值），但给用户带来的好处是更干净的 DOM 结构、更可控的 CSS 作用域、更准确的语义。理解了 Fragment，你就理解了一个设计原则：**框架的存在是为了让你不被底层约束限制——当类型系统和 UI 需求冲突时，好的框架提供的是零成本的妥协方案。**
