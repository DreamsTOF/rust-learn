# 练习 12: match 在 view 中

## 为什么要学这个

从上一个练习开始，你认识了 `view!` 宏的基本用法——写元素、写文本、嵌入表达式。但很快你就会发现，真实的应用不会一直显示静态内容：

- 根据用户是否登录，显示"你好"或"请登录"
- 根据网络请求的状态，显示加载中、成功、或错误页面
- 根据枚举类型的不同变体，渲染不同的 UI 结构

这些场景本质上是一件事：**根据数据的值，决定展示什么**。

Rust 有非常强大的工具来做这件事——`match` 表达式。本练习要回答：

1. **为什么有了 `if`，`match` 依然必不可少？** — `match` 比 `if` 强在哪？
2. **`match` 在 `view!` 里怎么用？** — 模式匹配和声明式 UI 如何结合？
3. **"穷尽性检查"对 UI 编程意味着什么？** — 为什么编译器是你的朋友？

---

## 从问题出发

### `if` 不够吗？

Rust 的 `if` 当然可以用在 `view!` 里：

```rust
view! {
    <p>
        { if num == 1 { "一" } else if num == 2 { "二" } else { "其他" } }
    </p>
}
```

这段代码能工作。但它有两个问题：

1. **可读性差** — 层层嵌套的 `if else`，一旦分支超过 3 个，眼睛就花了
2. **编译器不帮你检查覆盖** — `if` 没有穷尽性概念，少写一个分支不会报错

`match` 把这个问题从根本上解决了。

### `match` 在 view 中的样子

```rust
view! {
    <p>
        { match num {
            1 => "一",
            2 => "二",
            3 => "三",
            _ => "其他",
        } }
    </p>
}
```

在 `view!` 中，`match` 的出现方式跟任何 Rust 表达式一样——用 `{ }` 包裹。`view!` 宏看到 `{` 后就切换到"Rust 模式"，把里面的内容当作普通的 Rust 代码来编译。

所以这里的规则极其简单：

```
view! 的文本模式           view! 的 Rust 模式
┌──────────────┐          ┌──────────────────────┐
│ <p>"文本"</p> │          │ <p>{ Rust 代码 }</p>  │
└──────────────┘          └──────────────────────┘

在 Rust 模式里你可以写：
  • { num }                    ← 简单的变量
  • { num + 1 }                ← 表达式
  • { if cond { "A" } ... }    ← if 表达式
  • { match x { ... } }        ← match 表达式
  • { loop { ... } }           ← 循环（谨慎使用！）
```

> 所有 Rust 的**表达式**（有返回值的东西）都可以出现在 `{ }` 里。`match` 是表达式，`if` 也是表达式——这正是它们能嵌入 `view!` 的根本原因。

---

## `match` 的核心原理

### 1. 模式匹配，不止是"switch"

如果你从 C/JavaScript 过来，可能会觉得 `match` 就是 Rust 版的 `switch`。但它的能力远超 `switch`：

| | `switch` (C/JS) | `match` (Rust) |
|---|---|---|
| 匹配依据 | 整数、枚举常量 | 任意类型、任意模式 |
| 穷尽性检查 | ❌ | ✅ — 编译器强制所有分支都被覆盖 |
| 值解构 | ❌ | ✅ — 可以从元组、结构体、枚举中提取值 |
| 守卫条件 | ❌ | ✅ — `match x { n if n > 0 => ... }` |
| 返回值 | ❌（需要 break） | ✅ — 本身就是表达式 |

**关键的差异是"穷尽性"**。看这段代码：

```rust
match num.get() {
    1 => "一",
    2 => "二",
    // 忘了写 3 和默认分支
}
```

编译器报错：

```
error[E0004]: non-exhaustive patterns: `3i32` not covered
```

这是好事！编译器告诉你："你忘了处理 `num` 等于 3 的情况。"在 UI 编程中，这意味着一个状态没有被处理——用户可能看到空白或崩溃。

> **为什么这是 UI 编程的福音？** 前端 bug 最常见的来源之一就是"未处理的状态"。`match` 的穷尽性检查在编译期就堵住了这条路。如果写了 `_`（通配符），所有未列出的情况都会被兜底处理——你不可能"忘记"某个分支。

### 2. `match` 的每个分支必须返回相同类型

```rust
match num {
    1 => "一",            // &str
    2 => "二",            // &str
    _ => "其他",          // &str — 一致，编译通过
}
```

如果一个分支返回 `&str`，另一个返回 `i32`：

```rust
match num {
    1 => "一",            // &str
    2 => 42,              // i32 — 类型不匹配！
    _ => "其他",
}
```

编译器报错，因为 `match` 是一个表达式，所有分支必须推导出同一类型。这在 `view!` 中尤为重要——`view!` 需要知道 `{ }` 里表达式的类型，才能正确生成 DOM 操作代码。

> **实用技巧：** 如果你需要在 match 的不同分支返回不同类型的内容（例如，有时是 `<p>`，有时是 `<div>`），确保每个分支都返回 `impl IntoView` 即可——`IntoView` 是 `view!` 内容的统一类型。

### 3. 通配符 `_` 与变量的区别

```rust
match x {
    1 => "一",
    other => format!("数字: {other}"),  // other 捕获了所有未列出的值
}
```

```rust
match x {
    1 => "一",
    _ => "其他",  // 下划线：忽略匹配的值，不绑定变量
}
```

两者的区别：

| | `_` | 变量名（如 `other`） |
|---|---|---|
| 语义 | "我不关心这个值是什么" | "我把这个值绑定到变量上" |
| 性能 | 无开销 | 绑定变量 |
| 可读性 | "兜底处理" | "其他值我也想用" |

在 UI 中，如果你需要知道"其他"到底是什么值，用变量绑定；如果只是兜底，用 `_`。

## 响应式信号与 `match`

这个练习中有一个微妙但重要的细节：

```rust
let (num, set_num) = signal(1);

view! {
    <p>{ match num.get() { ... } }</p>
    <button on:click=move |_| set_num.set(2)>"设置 2"</button>
}
```

注意这里用的是 `num.get()` 而不是 `num`。为什么？

| 写法 | 含义 | 响应式行为 |
|---|---|---|
| `num` | 信号本身（Signal<i32>） | 显示当前值，并在值变化时更新 |
| `num()` | 同上，函数调用语法糖 | 显示当前值，并在值变化时更新 |
| `num.get()` | 显式调用 `.get()` | 读取一次当前值，**不跟踪更新** |

在练习的参考答案中，`match` 使用的是 `num.get()`。这意味着 `match` 只执行**一次**（在首次渲染时），之后即使 `num` 变化，`match` 也不会重新执行。

**这是故意为之吗？** 在这个练习中，按钮点击会导致组件重新渲染（因为信号是在组件内读取的），所以实际效果还是正确的。但在更复杂的场景中，如果你希望 `match` 结果随信号自动更新，应该使用 `num` 或 `num()` 而不是 `num.get()`。

> **设计取舍：** `.get()` 提供"快照"语义——读取一次值并冻结。这在事件处理函数中很常用（"在点击瞬间的值是什么"），但在响应式模板中要注意区别。

## `match` 在 `view!` 中的三种模式

```
模式一：match 返回文本
─────────────────────
{ match x { 1 => "一", _ => "其他" } }
→ 每个分支返回 &str，嵌入到文本节点中

模式二：match 返回元素
─────────────────────
{ match x {
    1 => view! { <span>"一"</span> },
    _ => view! { <span>"其他"</span> },
} }
→ 每个分支返回 view! 块（必须都在 view! 中）

模式三：match 返回组件
─────────────────────
{ match x {
    Status::Loading => view! { <Spinner/> },
    Status::Done(data) => view! { <Result data=data/> },
} }
→ 枚举变体匹配解构，返回不同组件
```

这个练习只涉及模式一，但它展示的机制可以扩展到所有三种模式。

---

## 一通百通

```
match 在 view! 中的本质 = Rust 的模式匹配 + view! 的嵌入表达式

你学会的其实是：
  view! 中的 { } 可以包含任意 Rust 表达式
  ↓
  match 是 Rust 表达式之一
  ↓
  你可以在 view! 中利用 Rust 的全部控制流能力
```

| 知识点 | 核心理解 |
|--------|---------|
| `match` 是表达式 | 不是语句，可以直接返回值的 |
| 穷尽性检查 | 编译器强制处理所有分支，减少 UI 状态遗漏 |
| 通配符 `_` | 兜底处理所有未列出的值 |
| 分支类型统一 | match 所有分支返回值类型必须相同 |
| `num.get()` vs `num()` | `.get()` 是快照，`num()` 是响应式读取 |

把这个模式记在心里：**遇到"根据数据决定展示什么"的问题，先用 `match` 想一想**。它比 `if` 更严格、更安全、更易读。后面的练习中，你会看到 `match` 在组件内配合信号、枚举、异步数据一起使用的更高级场景。
