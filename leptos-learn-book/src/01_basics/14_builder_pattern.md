# 练习 14: 构建器模式初阶

## 为什么要学这个

到目前为止，你创建 UI 都是用 `view!` 宏。宏好用——但也带来一个包袱：**你把 UI 描述完全交给了宏，如果有一天你不想用宏呢？**

这不是一个理论问题。在实际开发中，有几种场景会促使你考虑"脱离宏"：

- **编译时间** — 宏展开是编译器的工作，复杂的模板可能拖慢编译
- **调试透明性** — 宏展开后的代码不好直接断点调试
- **动态构造** — 有时你需要在运行时根据条件"拼装"UI 结构，宏在编译期就固定了结构
- **框架无关层** — 你正在写一个库，不想依赖 `view!` 的宏语法

Leptos 提供了一套**构建器 API（Builder API）** 作为 `view!` 的完全替代方案。它们不做宏做的任何事情——就是普通的函数调用、链式方法、Rust 代码。

这个练习回答：

1. **构建器 API 长什么样？** — `div().child(...)` 是怎样工作的？
2. **它和 `view!` 宏的本质区别是什么？** — 宏 vs 函数，各自的优劣是什么？
3. **什么时候应该用构建器，什么时候应该用宏？** — 场景决定选择。

---

## 从问题出发

### 构建器模式是什么

构建器模式（Builder Pattern）是 Rust 中非常常见的一种设计模式。基本思想是：

```
一个初始对象 → 链式调用方法（每次设置一个属性） → 最终产物
```

```rust
// 典型构建器模式
let config = ConfigBuilder::new()
    .host("localhost")
    .port(8080)
    .timeout(30)
    .build();
```

Leptos 的 HTML 构建器 API 遵循完全相同的模式：

```rust
// 不需要 view! 宏，纯 Rust 函数调用
div()                            // 初始：创建一个 <div> 构建器
    .child("Hello")              // 设置：添加一个子节点
    .class("container")          // 设置：添加 CSS 类
    .on(ev::click, handler)      // 设置：注册点击事件
// 不需要 .build()！最终值直接实现 IntoView
```

每个函数调用都返回自身（或自身的一个变体），所以可以无限链式下去。最终的结果实现了 `IntoView`，可以直接从组件函数中返回。

### 与 view! 的对比

```
view! 宏版本                构建器 API 版本
─────────────────           ────────────────────
view! {                     div()
    <div>                       .child(h1().child("标题"))
        <h1>"标题"</h1>         .child(p().child("描述"))
        <p>"描述"</p>           .child(button().child("点击")
        <button>"点击"</button>     .on(ev::click, handler))
    </div>
}                           // 直接返回
```

| 维度 | `view!` 宏 | 构建器 API |
|------|-----------|-----------|
| 语法 | HTML 风格，声明式 | Rust 风格，链式调用 |
| 编译速度 | 较慢（宏展开需要工作） | 较快（纯函数调用） |
| 类型检查 | 宏内是"半 Rust"环境 | 完全正常的 Rust 类型系统 |
| 动态结构 | 受限（宏展开时结构固定） | 灵活（可以在运行时拼装） |
| IDE 支持 | 取决于宏展开能力 | 完全的 Rust Analyzer 支持 |
| 学习曲线 | 需要理解宏语法规则 | 普通的 Rust 函数调用 |

## 构建器 API 的工作机制

### 导入路径

构建器函数不在 `prelude` 中，需要显式导入：

```rust
use leptos::ev;                 // 事件类型
use leptos::html::{div, p, h1, button};  // 元素构建器
use leptos::prelude::*;         // 信号、组件等基础功能
```

注意 `html` 模块里的每个函数名都与 HTML 标签名一一对应：

```
HTML 标签    →  leptos::html 中的函数
<div>        →  div()
<p>          →  p()
<h1>         →  h1()
<button>     →  button()
<svg>        →  svg()
<input>      →  input()
```

函数名故意做成小写、与 HTML 同名。这不是巧合——这样你从 `view!` 迁移到构建器时，不需要学习新的名字。

### `child()` —— 核心的树构建方法

`child()` 是构建器 API 中最核心的方法。它接受任何实现了 `IntoView` 的类型：

```rust
.child("文本")              // &str
.child(count)               // Signal<i32>（实现了 IntoView）
.child(h1().child("标题"))  // 另一个构建器（也实现了 IntoView）
```

树形结构通过嵌套 `.child()` 调用来构建：

```rust
div()
    .child(
        h1().child("标题")     // h1 是 div 的第一个子节点
    )
    .child(
        p().child("内容")      // p 是 div 的第二个子节点
    )
```

这等价于 HTML：

```html
<div>
    <h1>标题</h1>
    <p>内容</p>
</div>
```

**嵌套深度的处理：** 如果你需要 3 层以上的嵌套，方法的缩进会变得难以管理。这时 `view!` 的声明式语法在可读性上更有优势。

### `.on()` —— 事件绑定

```rust
button()
    .child("点击")
    .on(ev::click, move |_| {
        set_count.set(count.get() + 1);
    })
```

`.on()` 接受两个参数：

1. **事件类型** — `ev::click`、`ev::input`、`ev::submit`……对应 `ev` 模块中的常量
2. **事件处理函数** — `move |event| { ... }`，跟 `view!` 中的 `on:click=move |_| { ... }` 完全一样

> `ev::click` 对应的就是 `on:click` 在 `view!` 中的事件名。两者底层是同一套事件系统。

### 为什么不需要 `.build()`？

初学者最容易困惑的是：构建器模式通常需要最后调用一个 `.build()` 来生成最终产物。为什么 Leptos 的不需要？

答案在类型系统中。Leptos 的构建器函数直接返回一个实现了 `IntoView` 的类型：

```rust
pub fn div() -> HtmlElement<Div> { ... }
// HtmlElement<Div> 实现了 IntoView
// 所以可以直接从组件函数中返回
```

`HtmlElement<Div>` 已经是一个"完整的 DOM 元素"了——它在内部持有对真实 DOM 节点的引用。你不需要 `build()` 来"构造"它，`div()` 调用时它已经存在了。

> **设计决策：** 去掉 `.build()` 减少了 API 的认知负担。你 `.child(...)` 添加的子节点会在构建过程中逐步添加到 DOM 中。如果你需要"先准备好再插入"的场景，Leptos 也提供了 `.build()` 用于显式完成构建——但在直接作为视图返回时不是必需的。

## 事件处理中的闭包捕获

在构建器 API 中，事件处理的写法与 `view!` 中有一个细微差异需要注意：

```rust
// view! 中的事件
view! {
    <button on:click=move |_| set_count.set(count() + 1)>
        "点击"
    </button>
}

// 构建器中的事件
button()
    .child("点击")
    .on(ev::click, move |_| set_count.set(count.get() + 1))
```

两者都用了 `move` 闭包。这是因为信号的所有权需要移动到闭包中——`set_count` 默认是借用的，但闭包可能在组件被销毁后仍然存在（比如在事件队列中），所以需要 `move` 来获取所有权。

> **原则：** 在 Leptos 中，事件处理闭包几乎总是 `move` 的。这不是构建器 API 的特殊要求，而是 `view!` 中同样遵循的规则。

## 什么时候选择什么？

理解了两套方案之后，选择标准就很清晰了：

```
使用构建器 API 的场景
──────────────────
✅ 编译时间是瓶颈时 → 构建器不需要宏展开
✅ 需要动态构建 DOM → 构建器是普通函数，可以 if/match/loop 控制
✅ 在公共库中暴露 API → 不要求使用者处理宏
✅ 简单的页面结构（1-2 层嵌套）→ 构建器代码很清晰

使用 view! 宏的场景
─────────────────
✅ 嵌套层次深（3 层以上）→ 宏的声明式语法更易读
✅ 大量 attribute/prop → 宏的 HTML 风格写属性更自然
✅ 团队偏好声明式 → 多数前端开发者更熟悉 HTML
✅ 快速原型 → 宏帮你省去导入每个 html::* 函数的麻烦
```

**最诚实的判断标准：** 哪个让你的代码在 3 个月后回来看时，不需要心算就能理解？如果你在构建器中数括号，或者被宏的神秘错误吓到，那就用另一个。

## 一通百通

```
构建器 API = 把 "view! 宏生成的代码" 变成 "你手写的代码"

你学会的其实是：
  view! 不是唯一的 UI 编写方式
  ↓
  构建器 API 让你直接操控 DOM 构造过程
  ↓
  选择权在你手里——框架只提供工具，不强加范式
```

| 知识点 | 核心理解 |
|--------|---------|
| `div().child(...)` | 链式调用的核心模式 |
| 无需 `.build()` | `HtmlElement` 已实现 `IntoView` |
| `.on(ev::click, handler)` | 事件绑定与 view! 一致 |
| 构建器 vs 宏 | 两种方案都有适用场景，不是替代关系 |
| `move` 闭包 | 事件处理中所有权模型的必然要求 |

这是你第一次接触 Leptos 的非宏 API。后面学路由、表单、动画时，你会发现许多功能同时提供宏和纯 API 两种形式。**宏不是框架的全部，框架的核心是一组你可以在纯 Rust 中使用的函数和 trait。**
