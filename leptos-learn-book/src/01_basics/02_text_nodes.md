# 练习 02: 文本节点

## 为什么要学这个

文本是 UI 中最基础的元素——没有文本，网页就只是一堆空盒子。但在 `view!` 宏中，最简单的文本展示却需要一套你从未见过的语法。

这一节回答三个问题，它们将帮你彻底理解 `view!` 如何处理文本：

1. **为什么 `"Hello"` 必须加双引号，而不是直接写 `Hello`？** — 这涉及 Rust 宏的解析本质
2. **多个 `"..."` 并列写在一起会发生什么？** — 这不是多余的写法，而是刻意的设计
3. **空格去哪了？** — 为什么 `"Hello" "World"` 和 `"HelloWorld"` 是一样的？

把这三件事搞明白，你就掌握了 `view!` 宏处理文本的全部规则。后面所有练习中的文字内容，都只是这些规则的应用。

---

## 从问题出发

在 HTML 中写文本是最自然不过的事：

```html
<p>Hello, World!</p>
```

但在 `view!` 中，同一段文字必须写成：

```rust
<p>"Hello, World!"</p>
```

**多出来一对引号。**

为什么？因为 HTML 和 Rust 宏对"文本"的理解完全不同。

```
你眼中的文本                 view! 宏眼中的文本
┌──────────────────┐       ┌───────────────────────┐
│  Hello, World!   │       │  Hello → Rust 变量名    │
│                  │       │  , → 标点符号??        │
│  这是纯文本对吗？   │  ──►  │  World → 又是个变量?!  │
│                  │       │  ! → 宏?? 函数??       │
└──────────────────┘       └───────────────────────┘
```

HTML 解析器知道 `<p>` 和 `</p>` 之间的内容就是文本。但 Rust 宏不同——它看到 `<p>` 和 `</p>` 之间的所有内容，**默认当作 Rust 代码来解析**。

这就引出了核心问题：**宏需要一种方式，明确告诉你"这里不是代码，是文本"。**

双引号 `"..."` 就是那个信号。

---

## 1. 字符串文本 `"..."` — 为什么双引号是必须的？

### 先理解"默认是 Rust 代码"

`view!` 是一个 Rust 宏。Rust 宏的工作方式是对输入的 token 序列进行模式匹配和转换。

当 `view!` 宏遇到这样的输入：

```rust
view! {
    <p>Hello</p>
}
```

它的处理过程大致是：

1. 识别 `<p>` — 进入"HTML 元素"模式
2. 看到 `Hello` — **在 Rust 宏的 token 分类中，`Hello` 是一个标识符（ident）**
3. 把 `Hello` 当作变量名，在 Rust 作用域中查找
4. 没找到变量 `Hello` → 编译错误

**结论：** 不加引号的内容，宏一律当作 Rust 代码处理。想让宏知道"这是纯文本"，就必须给它一个 Rust 中表示"字符串字面量"的东西——也就是 `"..."`。

### 那 JSX 为什么不用引号？

React 开发者可能会困惑：JSX 可以直接写 `<p>Hello</p>`，为什么 `view!` 不行？

| | JSX | Leptos view! |
|---|---|---|
| 解析环境 | JavaScript 解析器，自带 JSX 语法支持 | Rust 宏，在标准 Rust token 流上工作 |
| 文本默认行为 | JSX 语法定义了"标签内的裸词是文本" | 宏默认把所有裸词当 Rust 标识符 |
| 嵌入表达式 | `{expression}` | `{expression}` |
| 文本需要 | 裸词即可 | `"双引号"` |

**根本原因：** JSX 是 JavaScript 语言规范的一部分（或通过 Babel 等工具在语法层面处理），浏览器和转译器知道如何处理它。而 `view!` 是一个 Rust 宏——它必须在 Rust 的语法规则下工作，不能发明新的 token 分类。双引号是 Rust 中表示"这是字符串"的唯一方式。

> **设计取舍：** Leptos 选择用 Rust 宏而不是自定义 DSL 解析器，是为了获得编译期类型检查和零运行时开销。代价就是文本需要多打一对引号。这是一个"正确的代价"——Rust 社区普遍认为显式优于隐式。

### `"..."` 内部可以写什么？

双引号内部就是标准的 Rust 字符串字面量，支持所有 Rust 字符串的转义序列：

```rust
// 普通文本
<p>"Hello, World!"</p>

// 转义字符
<p>"第一行\n第二行"</p>         // \n 换行
<p>"Tab\t缩进"</p>              // \t 制表符
<p>"双引号：\"引号\""</p>       // \" 转义双引号
<p>"反斜杠：\路径"</p>         // \ 反斜杠

// Unicode 转义
<p>"温度：\u{00B0}C"</p>       // °C
```

但注意：在浏览器中渲染时，只有 HTML 能识别的换行（`<br>`）才会真正换行。`\n` 在 HTML 中默认被当作空白符折叠。这一点跟 HTML 本身的文本渲染规则一致，不是 `view!` 的特殊行为。

## 2. 多行文本并列拼接 — 为什么可以写多个 `"..."`？

### 语法现象

```rust
<p>"这是第一行文本" "这是第二行文本，紧接在后面"</p>
```

两个字符串文本之间**没有操作符**，没有 `+`，没有 `,`，只是简单地并排放置。这在 Rust 中叫什么？

这叫**字符串字面量拼接**（string literal concatenation），是 Rust 语言本身支持的特性：

```rust
// Rust 中两个相邻的字符串字面量会自动拼接
let s = "Hello, " "World!";
// 等价于
let s = "Hello, World!";
```

`view!` 宏把这个行为完整地继承到了模板中。

### 为什么需要这个特性？

想象一个场景：你有一个很长的段落文字，不想写在一行里：

```rust
// 不这样做：超长一行
<p>"这是一段非常非常非常非常非常非常非常非常非常非常非常长的文本"</p>

// 而是这样：分行写，自动拼接
<p>
    "这是一段非常非常非常"
    "非常非常非常非常非常"
    "非常非常长的文本"
</p>
```

**作用：** 在不引入运行时字符串拼接的前提下，让你可以在源代码中优雅地分行。所有拼接都在编译期完成，零开销。

### 对比字符串插值

多行文本拼接和 `{ }` 插值是两个不同的概念，不要混淆：

```rust
// 拼接：多个字符串字面量 → 编译期合并
<p>"Hello" " " "World"</p>       // 结果：Hello World

// 插值：字符串字面量 + Rust 表达式 → 运行期计算
<p>"Hello, " {name} "!"</p>      // 结果：Hello, <name 的值>!
```

拼接是**编译期**的，插值是**运行期**的。拼接不需要 `{ }`，因为它是纯文本对纯文本；插值需要 `{ }`，因为表达式需要 Rust 求值。

## 3. 空格的微妙之处 — 为什么 `"Hello" "World"` 中间没有空格？

### 一个容易踩的坑

```rust
<p>"Hello, " "Leptos!"</p>
```

这段代码渲染出来是 `Hello, Leptos!`——中间有一个空格。

等等，空格哪来的？我们明明没有加空格操作符。

答案在于**第一个字符串末尾就包含了一个空格**：`"Hello, "` 末尾的空格。

如果把空格去掉：

```rust
<p>"Hello," "Leptos!"</p>
```

渲染结果是 `Hello,Leptos!`——中间没有空格。

### Rust 字符串字面量拼接的精确语义

Rust 的字符串字面量拼接（以及 `view!` 继承的这个行为）是**纯字符级拼接**，不会在中间插入任何分隔符：

```
"Hello," + "Leptos!" = "Hello,Leptos!"
"Hello, " + "Leptos!" = "Hello, Leptos!"
"Hello," + " Leptos!" = "Hello, Leptos!"
```

**控制空格的唯一方式：** 在字符串字面量内部把空格写进去。

### 为什么多行文本不会自动换行？

一个可能的疑问：既然我在源代码中把文本分成了多行，为什么渲染结果没有分行？

```rust
<p>
    "第一行"
    "第二行"
</p>
// 渲染结果：第一行第二行（同一行）
```

这是因为 `view!` 宏对多行文本拼接的处理是**纯粹的字符串连接**，它不关心你源码中的换行和缩进。源码中的空白（空格、换行、缩进）在宏解析时被忽略了（就像 Rust 本身忽略多余的空白一样）。

如果你需要换行，要么用 `<br/>`，要么在文本中用 `\n`（但 HTML 中 `\n` 默认不显示为换行）。

## 回顾总结

| 知识点 | 规则 | 示例 | 说明 |
|--------|------|------|------|
| 字符串文本 | 用 `"..."` 包裹 | `<p>"Hello"</p>` | 告诉宏"这是文本" |
| 多行拼接 | 多个 `"..."` 并列 | `<p>"A" "B"</p>` → `"AB"` | 编译期字符串连接 |
| 空格控制 | 在引号内加入空格 | `"Hello, " "World"` → 有空格 | 拼接不自动加分隔符 |
| Rust 代码嵌入 | 用 `{ }` 包裹 | `<p>{name}</p>` | 运行期表达式求值 |
| 转义序列 | 标准的 Rust 转义 | `"\n"` `"\t"` | 在字符串内使用 |

**一通百通的核心：** `view!` 宏文本处理的所有规则，都可以追溯到一个基本原则——**宏不知道什么是"文本"，它只知道 Rust 的 token 分类。** 因此：

- 想表达"这是字符串"→ 用 `"..."`（Rust 的字符串字面量）
- 想表达"这是代码"→ 用 `{ }`（Rust 的块表达式）
- 想表达"这是多个字符串"→ 并列写，宏继承 Rust 的字面量拼接规则

掌握了这个原则，你永远不会困惑为什么 `view!` 的文本语法长这样。这不是 Leptos 的任性设计，而是 Rust 宏系统下最自然的选择。
