# 练习 04: 元素嵌套

## 为什么要学这个

单个元素能做的事很有限。真正的网页是一棵树——`<section>` 包含 `<div>`，`<div>` 包含 `<p>`，`<p>` 包含文本。组件化的第一步，就是理解这种层级结构如何在 `view!` 中表达。

这一节回答四个问题：

1. **为什么 UI 天然是树形结构？** — 从盒模型到嵌套的设计必然性
2. **`view!` 中的缩进只是装饰吗？** — 不，它是层级结构在代码中的映射
3. **语义元素（`<section>`）和通用容器（`<div>`）什么区别？** — 为什么需要不同的嵌套容器
4. **多层嵌套在编译期发生了什么？** — `view!` 如何把树形模板编译成类型安全的 DOM 树

理解元素嵌套，就是理解 UI 的本质：**无限递归的盒子。** 每一层 `>` 都是"包含"关系，最终构成从 `<body>` 到最小文本节点的完整路径。

---

## 从问题出发

最简单的网页结构：

```
┌─────────────────────────────────────┐
│  <body>                             │
│  ┌───────────────────────────────┐  │
│  │  <section id="main">          │  │
│  │  ┌───────────────────────┐    │  │
│  │  │  <div class="card">   │    │  │
│  │  │  ┌─────────────────┐  │    │  │
│  │  │  │  <p>             │  │    │  │
│  │  │  │  "这是一段文本"    │  │    │  │
│  │  │  │  </p>            │  │    │  │
│  │  │  └─────────────────┘  │    │  │
│  │  │  </div>               │    │  │
│  │  └───────────────────────┘    │  │
│  │  </section>                   │  │
│  └───────────────────────────────┘  │
│  </body>                            │
└─────────────────────────────────────┘
```

这不是一个"巧合"的布局——它是 Web 的盒模型（box model）和文档流（document flow）的自然结果。

**任何 UI 都是树。** 无论是 HTML DOM、Flutter 的 Widget 树、React 的虚拟 DOM 树，还是 Leptos 的组件树。理解嵌套就是理解 UI 的基本组织方式。

---

## 1. 为什么 UI 天然是树形结构？

### 盒模型的递归本质

HTML 的布局基于盒模型——每个元素都是一个矩形盒子。盒子可以包含其他盒子，被包含的盒子还可以再包含盒子：

```
┌─── 盒子（父元素）────────────────────┐
│  ┌─── 盒子（子元素）────────────────┐  │
│  │  ┌─── 盒子（孙元素）────────────┐  │  │
│  │  │  内容区域                      │  │  │
│  │  └────────────────────────────┘  │  │
│  └────────────────────────────────┘  │
└────────────────────────────────────┘
```

**为什么是递归的？** 因为这是最自然的"包含"关系的数学表达。一个页面不可能用线性结构（平铺的列表）来表达——那样你无法表达"这个段落属于这个区块，而不是紧挨着它"。

### 树形结构的三个好处

1. **继承** — 父元素的样式（字体、颜色、背景）默认被子元素继承
2. **作用域** — 子元素的布局相对于父元素定位（相对定位/绝对定位）
3. **层级** — z-index、堆叠上下文由嵌套层级决定

### 对比线性结构

```
线性（扁平）结构              树形（嵌套）结构
┌─────────────────┐        ┌─────────────────┐
│ <section>       │        │ <section>       │
│ <div>           │        │   └─ <div>      │
│ <p>             │        │      └─ <p>     │
│ "文本"          │        │         └─ "文本"│
│ </section>（关   │        └─────────────────┘
│ 闭了谁？）       │        每个结束标签对应
│ </div>          │        一个明确的开标签
│ </p>            │
└─────────────────┘
```

肉眼可见，树形结构更清晰：缩进和闭合标签一起告诉你"谁属于谁"。

## 2. `view!` 中的缩进 — 不止是好看

在 `view!` 中，嵌套通过缩进来表达：

```rust
view! {
    <section class="container" id="main">
        <div class="card">
            <p>"这是嵌套在 section > div 内的段落"</p>
        </div>
    </section>
}
```

**关键点：** `view!` 宏不需要缩进来工作（它根据标签的配对关系来解析）。缩进是**写给开发者看的**。

但缩进的意义远超"好看"：

### 缩进反映层级深度

```
缩进深度 0: view! {               ← 宏入口
缩进深度 1: <section>             ← 第一层元素
缩进深度 2:     <div>             ← 第二层元素
缩进深度 3:         <p>           ← 第三层元素
缩进深度 4:             "文本"     ← 文本节点
缩进深度 3:         </p>
缩进深度 2:     </div>
缩进深度 1: </section>
缩进深度 0: }
```

每一级缩进代表 DOM 树中的一个层级。眼睛扫过去就能知道"这个元素在第几层"。

### 错误的缩进 vs 正确的结构

```rust
// ❌ 错误的缩进——结构混乱
view! {
    <section>
        <div>
    <p>"这是哪一层？"</p>
        </div>
    </section>
}

// ✅ 正确的缩进——层级一目了然
view! {
    <section>
        <div>
            <p>"这是第三层"</p>
        </div>
    </section>
}
```

虽然两段代码在宏解析后结果相同（缩进不影响 DOM 结构），但错误的缩进会让阅读代码的人产生误解。

> **最佳实践：** `view!` 中的缩进应当精确反映 DOM 树的结构。每深入一层，增加一个缩进级别。这样代码即文档。

## 3. 语义元素 vs 通用容器

嵌套时，你选择用什么"盒子"来装内容，不是随意的。HTML5 定义了一组语义元素来表示不同类型的区块：

| 元素 | 语义 | 典型用途 |
|------|------|---------|
| `<div>` | 无语义的通用容器 | 布局、分组、CSS 钩子 |
| `<section>` | 主题相关的区块 | 章节、标签页、文章分区 |
| `<article>` | 独立的内容单元 | 博客文章、新闻、评论 |
| `<nav>` | 导航链接区域 | 菜单、目录 |
| `<aside>` | 附属内容 | 侧边栏、广告、相关链接 |
| `<main>` | 页面主体内容 | 每个页面唯一的主内容区域 |
| `<header>` | 介绍性或导航性内容 | 页面标题、logo、导航 |
| `<footer>` | 底部信息 | 版权、联系方式、相关链接 |

### 为什么要有语义元素？

```rust
// ❌ 只有 div
view! {
    <div id="header">
        <div class="nav">...</div>
    </div>
    <div id="main">
        <div class="article">...</div>
    </div>
    <div id="footer">...</div>
}

// ✅ 语义元素
view! {
    <header>
        <nav>...</nav>
    </header>
    <main>
        <article>...</article>
    </main>
    <footer>...</footer>
}
```

语义元素的好处：

1. **可访问性** — 屏幕阅读器可以理解页面结构，让用户快速导航到不同区块
2. **SEO** — 搜索引擎更好地理解内容层次
3. **可维护性** — 其他开发者阅读代码时立即理解每个区块的用途
4. **默认样式** — 浏览器为每个元素提供合理的默认显示方式

> **原则：** 先用语义元素（`<section>`、`<article>`、`<nav>`），当没有合适语义时再用 `<div>`。`<div>` 是"不知道用什么时的选择"，不是"默认选择"。

## 4. `view!` 如何编译嵌套结构

在了解了嵌套的表层语法后，值得看看底层发生了什么。这对于理解 Leptos 如何处理复杂的 DOM 树有帮助。

### 编译期：从模板到类型

`view!` 宏将嵌套的 HTML 模板编译成类型安全的 Rust 代码：

```rust
// 你写的
view! {
    <section id="main">
        <div class="card">
            <p>"文本"</p>
        </div>
    </section>
}

// 宏展开（示意，简化）
// 1. 创建一个 <section> 元素
// 2. 创建一个 <div> 元素
// 3. 创建一个 <p> 元素
// 4. 创建一个文本节点 "文本"
// 5. 把文本节点添加为 <p> 的子元素
// 6. 把 <p> 添加为 <div> 的子元素
// 7. 把 <div> 添加为 <section> 的子元素
```

**关键点：** 这个展开过程发生在编译期，不是运行时。所以：

- 嵌套关系的验证在编译期完成（标签有没有正确配对）
- 生成的代码是精确的 DOM 操作序列，没有中间表示
- 子元素的插入顺序由宏自动生成，不需要手动管理

### 运行时：从类型到 DOM

在运行时，`view!` 生成的对象被挂载到文档中。最终生成的 DOM 树是这个样子：

```html
<section id="main">
    <div class="card">
        <p>文本</p>
    </div>
</section>
```

跟用 HTML 写出来的完全一样。Leptos 不会像 React 那样保留虚拟 DOM，而是直接操作真实 DOM 节点。

## 回顾总结

| 知识点 | 核心思想 | 实践建议 |
|--------|---------|---------|
| 树形结构 | UI 天生是递归的盒模型嵌套 | 用树形思维设计布局 |
| 缩进 | 反映 DOM 层级，代码即文档 | 每层嵌套缩进一级 |
| 语义元素 | 用元素名表达区块的含义 | 优先 `<section>`、`<article>`、`<nav>` |
| `<div>` | 无语义的通用容器 | 没有合适语义时再用 |
| 编译原理 | 嵌套在编译期转为类型安全 DOM 操作 | 依赖编译器检查结构错误 |

**一通百通的核心：** 元素嵌套是 UI 的基本组织方式。无论是在 Leptos、React、Vue 还是原生 HTML 中，你都在做同一件事——**把盒子放进盒子。** `view!` 的嵌套语法只是让你用 Rust 代码自然地表达这个结构。缩进帮助你维护可读性，语义元素帮助你和浏览器理解"这个盒子是干什么的"。

当你在第 06 节学到组件嵌套时，你会发现那只是元素嵌套的推广——元素嵌套是"HTML 标签包含 HTML 标签"，组件嵌套是"自定义组件包含自定义组件"。原理完全一样。
